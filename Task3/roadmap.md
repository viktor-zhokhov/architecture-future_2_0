# Роадмап изменений технологического ландшафта

Роадмап опирается на технический радар (`TechRadar.drawio`) и целевую архитектуру из Task1–Task2. Разбит на этапы с привязкой к целям бизнеса: промежуточное состояние (пара месяцев) и финальное состояние (год).

## Этап 0 (месяцы 0–1). Архитектурное проектирование и согласование

| | |
| --- | --- |
| **Ожидаемые результаты** | Согласованная целевая архитектура (C4 Container), определены границы доменов и потоки данных между ними, приоритизирован список проблем |
| **Ответственные команды** | Архитекторы компании, тех.лиды доменов (клиника, финтех, ИИ) |
| **Необходимые ресурсы** | Время архитекторов на проектирование, серия согласований с бизнес-стейкхолдерами |

**Обоснование.** Без согласованной целевой архитектуры и границ доменов любые последующие технические изменения рискуют закрепить существующую связанность систем. Этот этап не даёт прямого технического результата, но снижает риск дорогостоящих переделок на следующих этапах — то есть влияет на итоговую скорость и стоимость всего перехода.

## Этап 1 (месяцы 1–3). Облачная платформа и доменная интеграция

| | |
| --- | --- |
| **Ожидаемые результаты** | Развёрнута облачная инфраструктура (IaaS/Terraform), готовы Cloud DWH/Lakehouse и доменная шина событий/API-шлюз с RBAC/ABAC |
| **Ответственные команды** | Платформенная/DevOps-команда, команда данных |
| **Необходимые ресурсы** | Облачный бюджет, инженеры по Terraform, специалисты по облачной безопасности |

**Обоснование.** Это фундамент, на котором строится и портал самообслуживания, и независимость доменов. Облако напрямую снижает затраты на поддержку устаревшего оборудования и повышает надёжность критичных сервисов (отказоустойчивость, резервное копирование — регуляторное требование к медицинским и финансовым данным). Без доменной шины любое подключение нового домена продолжит требовать изменений в DWH.

## Этап 2 (месяцы 3–6). Запуск портала самообслуживания (MVP на домене «Финтех»)

| | |
| --- | --- |
| **Ожидаемые результаты** | MVP портала самообслуживания; домен «Финтех» подключён к витрине данных агрегированным потоком; бизнес-пользователи строят первые отчёты в рамках уровня доступа |
| **Ответственные команды** | Команда портала (фронтенд/бэкенд), команда данных (ETL), домен «Финтех» |
| **Необходимые ресурсы** | Разработчики портала, аналитики данных, тестовый контур с реальными агрегированными финансовыми показателями |

**Обоснование.** Финтех выбран первым доменом для MVP, так как не содержит медицинских данных и требует минимального контракта — это позволяет быстро показать бизнесу работающий портал и проверить архитектуру на реальном потоке, прежде чем подключать более чувствительный домен «Клиника». Прямо влияет на скорость принятия управленческих решений — часть отчётов перестаёт строиться часами уже на этом этапе.

## Этап 3 (месяцы 6–9). Подключение «Клиники» и прямого контракта с ИИ-сервисами

| | |
| --- | --- |
| **Ожидаемые результаты** | Немедицинские операционные метрики клиники доступны в портале; выстроен прямой контракт «Клиника» ↔ «ИИ-сервисы» для анализа медицинских данных, минуя DWH и витрину |
| **Ответственные команды** | Домен «Клиника», ИИ-команда, платформенная команда |
| **Необходимые ресурсы** | Время на разбор и очистку данных клиники, тестирование контракта с ИИ-сервисами на реальных сценариях |

**Обоснование.** Это этап, критически важный для качества медицинских сервисов: архитектурно гарантируется, что медицинские данные не попадают в аналитику (требование бизнеса), при этом ИИ-диагностика получает прямой, быстрый доступ к нужным данным без промежуточного слоя. Одновременно клиника получает свою часть портала самообслуживания.

## Этап 4 (месяцы 9–12). Готовность к новым партнёрам и снижение технического долга

| | |
| --- | --- |
| **Ожидаемые результаты** | Воспроизводимый шаблон подключения нового домена (по образцу «Финтех»/«Клиника»); пилотная интеграция с одним партнёром (фармацевтическая компания или производитель электроники); сокращён объём бизнес-логики, остающейся в legacy DWH |
| **Ответственные команды** | Архитекторы, интеграционная команда, юридическая поддержка (партнёрские соглашения) |
| **Необходимые ресурсы** | Время на документирование контракта интеграции, ресурсы на пилотный проект с партнёром |

**Обоснование.** Прямо реализует цель бизнеса «масштабирование для новых бизнесов»: если типовой контракт подключения домена уже отработан на двух реальных примерах, добавление нового партнёра перестаёт быть отдельным архитектурным проектом — это сокращает time-to-market для новых направлений и снижает затраты на каждую следующую интеграцию.

## Сквозная линия (месяцы 1–12). Меры для качества медицинских и финансовых сервисов

| | |
| --- | --- |
| **Ожидаемые результаты** | Резервное копирование и геораспределённое развёртывание для критичных сервисов; аудит доступа к медицинским и финансовым данным; мониторинг SLA |
| **Ответственные команды** | SRE / информационная безопасность |
| **Необходимые ресурсы** | Бюджет на мультирегиональную инфраструктуру, security-аудит |

**Обоснование.** Идёт параллельно всем остальным этапам начиная с Этапа 1, а не после них — устранение регуляторных и надёжностных рисков нельзя откладывать до конца проекта, так как компания уже сегодня работает с медицинскими и финансовыми данными, подпадающими под требования регуляторов.
